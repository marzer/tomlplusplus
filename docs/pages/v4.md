@page v4 Possible changes for v4
@tableofcontents

Each change on this page would improve toml++, and most would also break something that users rely on today. They wait
for the next major version, and none of them is decided. The appendix at the end lists related requests that aren't
planned for v4.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@section v4-library Library

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-path-subpath Static path::subpath() overload

`toml::path::subpath(const_iterator, const_iterator)` doesn't use the path it's called on, so it could be a static member
function ([#310](https://github.com/marzer/tomlplusplus/pull/310)). Calls through an object would still compile.

The exported symbol would change from a const member function to a static one, so programs linked against a shared build
of toml++ would need rebuilding.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-paths Paths and empty keys

A `toml::path` is meant to be relative to the node it's applied to, but TOML allows empty keys, and that makes some
paths ambiguous. `toml::path("")` is one empty key. A default-constructed path is empty, and so is one built from a
string that fails to parse. An empty path selects the node it's applied to, unless that node is a value or an empty
container. `str()` loses the `.` between an empty key and an index, so `a..[1]` prints as `a.[1]`, which is a
different path.

Some other quirks: a `.` directly before an index is ignored, so `a.[1]` is the same path as `a[1]`. The string
overloads of `at_path()` select nothing for a string that fails to parse, and the path overloads select the node itself
for the empty path that string gives. Assigning such a string to a path empties it, and appending one leaves the path
unchanged.

The path tests pin all of this as v3.4.0 had it, and v3 keeps it that way.

How paths work, and how they should work, needs a review from the ground up. Any change here would change what
existing paths select or how they print.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-table-reverse Reverse iteration over tables

A `toml::table` iterator returns its key-value pair as a proxy object stored inside the iterator. `std::reverse_iterator`
dereferences a temporary copy of the iterator, so the reference it returns outlives the proxy, and `std::views::reverse`
does the same. Returning the proxy by value would fix it.

The iterators' `reference` type would change, so loops like `for (auto& [k, v] : tbl)` would stop compiling.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-parse-result-conversions parse_result conversions without exceptions

With exceptions disabled, `toml::parse_result` converts implicitly to `table&`, `table&&` and `const table&`, and none of
the conversions is ref-qualified. So `toml::table t = result;` is ambiguous, and `toml::table& t = toml::parse(doc);`
compiles and dangles. Ref-qualifying the conversions fixes both, though direct-initialisation from an rvalue stays
ambiguous.

Code that takes a `table&&` from an lvalue `parse_result`, or a `table&` from a temporary one, would stop compiling.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-mixed-exceptions Mixing exception settings

Code built with and without exceptions can share a program, because most of what differs between the two is in inline
namespaces named after `TOML_EXCEPTIONS`. These differences aren't:

- `toml_formatter`, `json_formatter` and `yaml_formatter` have an extra member when exceptions are off, so formatting in
  both kinds of code can overrun a formatter on the stack. With exceptions off, code that sets `TOML_ENABLE_PARSER=0`
  also disagrees with a compiled toml++ about their layout.
- Nothing separates code built with compiler exceptions from code built without them. The parser's layout differs
  between the two even with `TOML_EXCEPTIONS=0` in both. `array::at()` and `table::at()` throw in one and assert in the
  other, and a program with both gets one behaviour everywhere, whatever `TOML_EXCEPTIONS` says.
- With exceptions off, the parser holds its error in an `optional`, so `TOML_OPTIONAL_TYPE` changes its layout too.

Separating these properly changes the layout or the exported names of the formatters and of `at()`, so it breaks the
shared library's ABI.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-date-time-comparison Comparing date-times as instants

`toml::date_time` compares field by field. `1979-05-27T07:32:00Z` and `1979-05-27T00:32:00-07:00` are the same instant
but compare unequal, and `<` orders by local date and time before the offset. Offset date-times could compare as
instants instead, with some rule for comparing them to local ones.

Equality of tables and arrays holding date-times would change with it, and so would the order of sorted containers of
them.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-node-storage Node storage

Parsing allocates once for every node, every table entry, every non-empty array, and every key or string too long for
the small-string buffer. A parsed 8 MB document holds about 455,000 allocations, the fewest the current types allow.
These would need fewer:

- tables as a sorted vector of key-value pairs, with one allocation per table where `std::map` makes one per entry
- tables and arrays holding their values in place, where each value is a separately allocated node today
- keys and strings that refer into one copy of the document
- one source path per document, where every node's source region holds a `std::shared_ptr` to it today, and each copy
  is an atomic increment

Each changes the layout of a public type. The first two would also make inserting into a table or array invalidate
references to its other elements, which stay valid today, and the third would change what `toml::key` and
`toml::value<std::string>` hold.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-node-interface A smaller node interface

`toml::node` has 35 virtual functions: the destructor, `type()`, twelve `is_*()` checks, eighteen `as_*()` casts and
three `is_homogeneous()` overloads. So there are ten vtables of 38 entries, for `node` and its nine concrete types, and
each concrete type has its own copy of every override, most of them a single return statement. In a program that
parses and prints, they come to as much as 20 KB.

Only `type()` and `is_homogeneous()` need to be virtual. The checks and casts could be inline functions that test
`type()`. That changes every node vtable and removes exported virtual functions, so it breaks the shared library's ABI.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-noexcept-constructors Constructors that allocate under noexcept

The default and move constructors of `toml::table` and `toml::array` are `noexcept`. With the MSVC STL, `std::map`
allocates in both of its own, and in debug builds `std::vector` does too, so running out of memory while constructing
or moving a table calls `std::terminate()` where it could throw `std::bad_alloc`.

Dropping the `noexcept` would let it throw. Code that tests these constructors with `std::is_nothrow_*` or
`noexcept()` would see the change, and so would containers that move elements only when moving is `noexcept`.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-float16 Detecting _Float16

`TOML_ENABLE_FLOAT16` defaults to `0`, so `_Float16` support is opt-in. Detecting it from the compiler's predefined
`__FLT16_*` macros breaks GCC 7 to 12 on ARM, which define the macros in C++ without accepting the type there
([#57](https://github.com/marzer/tomlplusplus/issues/57), [#178](https://github.com/marzer/tomlplusplus/issues/178),
[#186](https://github.com/marzer/tomlplusplus/issues/186)). GCC 13 and newer, and Clang, define the macros only where
they accept the type, so detection could be limited to them.

Turning it on by default would break code that sets `TOML_SMALL_FLOAT_TYPE` to `_Float16`, or to `std::float16_t` in
C++23 with GCC, because the library would then define its traits for that type twice.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-unicode-bare-keys Unicode bare keys

With `TOML_ENABLE_UNRELEASED_FEATURES`, bare keys can hold the non-ASCII characters that
[toml-lang/toml#891](https://github.com/toml-lang/toml/pull/891) allowed. TOML backed that change out before 1.1.0
([toml-lang/toml#979](https://github.com/toml-lang/toml/pull/979)), because there was no agreement on normalisation or
on which characters to allow. No released or draft version of TOML has these keys, so v4 could drop them.

Documents that use such keys would stop parsing until the keys are quoted.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-lifetime-annotations Lifetime annotations

A view or reference into a temporary table dangles at the end of the full expression.
`auto v = toml::parse(doc)["key"];` compiles without a warning, and leaves `v` pointing into a destroyed table.

Clang can warn about code like this if the library annotates itself: `[[gsl::Owner]]` on tables and arrays,
`[[gsl::Pointer]]` on views, and `[[clang::lifetimebound]]` on the member functions that hand out views and references.

Such code would start to get warnings, which fails a build that treats warnings as errors.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-events Event interface

Parsing always builds the whole document as a tree of nodes. An event interface in the style of SAX would report each
table, key and value as the parser reaches it, so a program could read a document without holding all of it in memory
([#107](https://github.com/marzer/tomlplusplus/issues/107)).

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-custom-types Custom types

A user-defined type, such as a point with `x` and `y` members, has to be read and written one member at a time
([#175](https://github.com/marzer/tomlplusplus/issues/175)). A conversion written once for each type could let
`value<T>()` and `value_or()` return such a type, and let tables and arrays take one directly.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-reflection Reflection

With C++26 reflection, toml++ could convert between tables and structs without code written for each type
([#324](https://github.com/marzer/tomlplusplus/pull/324)).

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-output-order Output order and float precision

The formatters write a table's entries in key order, which is how `toml::table` stores them. Tables don't record the
order their entries were inserted in. Floats are written with enough digits to read back as the same value, or rounded
to at most six significant digits with `format_flags::relaxed_float_precision`.
[#304](https://github.com/marzer/tomlplusplus/issues/304) asks for a choice of key order, insertion order included. It
also asks for a way to set float precision, as `std::setprecision` does for a stream.

Writing in insertion order would need tables to record it, which changes their layout. Floats written with fewer digits
than they need don't read back as the same values.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-library-std-format std::format support

Printing a node needs a `std::ostream`, with or without one of the formatters. Specialisations of `std::formatter`
would let C++20 code pass nodes to `std::format()`, and C++23 code to `std::print()`, with a format specifier to pick
TOML, JSON or YAML ([#325](https://github.com/marzer/tomlplusplus/issues/325)).

@section v4-cmake CMake

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-cmake-minimum Minimum CMake version

The minimum is CMake 3.14. Raising it to 3.21 would let `project()` set `PROJECT_IS_TOP_LEVEL`, so
`cmake/project-is-top-level.cmake` could go. Copying runtime DLLs next to the Windows test executables would also stop
needing a version check.

It would break anyone building with CMake 3.14 to 3.20, which includes the 3.16 that Ubuntu 20.04 ships.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-cmake-options Option names

The options use three naming styles. Most have a lowercase prefix, like `tomlplusplus_INSTALL`, `tomlplusplus_BUILD_LIB`
and `tomlplusplus_INSTALL_CMAKEDIR`. `TOMLPLUSPLUS_BUILD_MODULES` is all uppercase, and `BUILD_EXAMPLES` and
`BUILD_FUZZER` have no prefix. CMake convention is all uppercase, so every option would become `TOMLPLUSPLUS_*`.

Each renamed option breaks the scripts and recipes that set it, and one of them lives outside this repository. The
OSS-Fuzz builder image copies `fuzzing/build.sh` from master, and CIFuzz runs master's copy against every pull request.
`BUILD_FUZZER` has to keep working until master's script stops using it.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-cmake-package-location Package files for header-only installs

A header-only install puts the CMake package files in `lib/cmake/tomlplusplus`. They are the same on every architecture,
so `share/cmake/tomlplusplus` suits them better, and Meson already uses it for header-only installs.

`find_package()` searches both locations. Anything that hard-codes the current path, such as a `tomlplusplus_DIR`
setting, would break.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-cmake-cpack CPack

The top-level build includes CPack with no configuration, which adds a `package` target nobody has set up. Removing it
takes that target away from anyone who runs it.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@section v4-meson Meson

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-meson-version-check Version check

The `tomlplusplusConfigVersion.cmake` that Meson installs accepts any newer version, so `find_package(tomlplusplus 2)`
finds 3.4. The one CMake installs only accepts the same major version, which matches the ABI namespace.

Making Meson's match would refuse version requests that succeed today.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-meson-examples Installed examples

With `-Dbuild_examples=true`, Meson installs the example programs into `bin/`. They exist to show the API, and the CMake
build doesn't install them. Stopping it would remove files from installs that include them today.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-meson-default-library Library type as a subproject

`meson.build` sets `default_library=shared` in its `default_options`. That is Meson's default anyway, so it only matters
when toml++ is a subproject. There it overrides the parent project's `default_library`, and with Meson older than 1.8 it
also overrides `-Ddefault_library` on the command line. Without it, the parent chooses.

Parent projects that build the library with `build_lib=true` and ask for static libraries would then get a static
toml++, where they get a shared one today.

<!-- --------------------------------------------------------------------------------------------------------------- -->

@section v4-repository Repository

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-repository-tipi Tipi.build

The `.tipi/` directory and the Tipi.build instructions in the README and on the main page support a package manager the
project doesn't test against. Removing them would break Tipi users.

@section v4-appendix Appendix

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-appendix-comments Preserving comments

Parsing discards comments and whitespace, so a document that is read and written out again loses them. Keeping them
properly needs a large rewrite, and partial support would be worse than none
([#28](https://github.com/marzer/tomlplusplus/issues/28), [#312](https://github.com/marzer/tomlplusplus/pull/312)).

<!-- --------------------------------------------------------------------------------------------------------------- -->

@subsection v4-appendix-table-iteration Table iteration by value

A `toml::table` iterator's proxy pair holds references to the key and the node, which keeps the `std::unique_ptr` that
owns each node out of the API. So `for (auto kv : tbl)` copies two references, and generic code that asks for a copy
expects a copy of the element ([#31](https://github.com/marzer/tomlplusplus/issues/31)). It's the same proxy that
breaks reverse iteration. Nodes held by value, for example as a discriminated union, would let tables do without it.
